## What changed
`src/story/three-piece.ts` (126 lines, no LLM) does the following:
- Picks the first stack frame in a file the transcript edited (`:42-46`).
- Finds the last edit whose added lines contain that frame line's exact text (`:49-58`).
- **Asked** = the last non-machine user message before that edit, reduced to the paragraph with the most identifier overlap (`:79-84`).
- **Understood** = the last assistant message before the edit, in full (`:88-94`).
- **Happened** = the error text plus the frame and hunk (`:98-102`).

Sandbox proof, decoys, the mechanism and cause gates, and the pre-merge checker are all out of the story.

## (d) Re-run (deterministic)
`bash scripts/three-piece-all.sh /tmp/tp8` reproduced exactly the same JSON as `artifacts/three-piece/*.json` for all 15 cases (generated_at excluded): 12 complete, 1 silent edit, 2 pre-existing. **The numbers are reproducible.** The question is what they mean.

## (b) Is the metric meaningful? Mostly no
- **The "valid citation" checks are close to tautological.**
  - `asked.valid = ask.text.includes(para)`, where `para` is a trimmed paragraph cut out of `ask.text` itself (`three-piece.ts:82-83`), so it is true by construction.
  - `happened.valid: true` is unconditional (`:101`).
  - The only real filter is `understood` having ≥15 words (`:92`), plus a frame line being found in an edit.
  - So "12/15 all three cited" really means "13/15 frame lines were textually written by a transcript edit, minus 1 where the agent wrote <15 words". It does not check that any piece explains the bug.
- **Content isn't model-written:** all three pieces are verbatim and selected by heuristics (latest message, identifier overlap). The *explanation* ("the gap between 2 and 3") is written by the builder, e.g. README.md:23 "The agent pictured one click at a time…" and the deck's vote-race slide. That sentence is not engine output.
- **Linking:** exact-text match of the deployed frame line against `+` lines; the last match wins.
  - It is correct on every case I checked. Using `grep` on the raw transcripts, the culprit line's first write is the linked edit: webhook-block L123, vote-race L123, macro-leapday L3567, outcome-keys L110.
  - It is trivial given the input: the builder-authored error.json names the exact file:line, and 11/13 frames are `def`/`function` lines, so "the edit that wrote it" is "the edit that wrote the function".
  - A wrong link could pass when a later edit changes the body without re-adding the def line. The link would then point at the earlier function-creating edit. That's not seen in my sample, but nothing guards against it.
- **Hand check of 6 cases** (vote-race, webhook-block, macro-leapday, caps-unknown, outcome-keys, xirr), read against the transcripts and ground truth:

| case | link correct | Asked relevant to the bug | Understood shows the faulty belief |
|---|---|---|---|
| vote-race | yes | partly ("upvote") | partly (check-then-create plan; no concurrency mention) |
| webhook-block | yes | no (generic build prompt) | partly (mentions the webhook in a 1,385-char planning note; same message as vote-race) |
| macro-leapday | yes | no (Stock Research sub-agent paragraph) | no ("Adding `_refresh_macro`…") |
| caps-unknown | yes | no (Phase 0 goal) | no (5,251-word message) |
| outcome-keys | yes | no (site structure spec) | **yes** (agent says it is switching keys to indices; the code uses `outcome.detail`) |
| xirr | yes | no (Phase 0 goal) | no (sectors dict / sim engine) |

**Hand-checked accuracy:**
- Edit link: 6/6 (but trivial).
- A useful asked→understood→happened explanation: about 1.5–2/6, roughly 30%.
- Extrapolated: **about 4–5/15 genuinely explanatory**, against the claimed 12/15.
- webhook-block and vote-race get *identical* Asked and Understood pieces, which shows the pieces describe the edit, not the bug.

## (c) Hard-coding, leakage, tuning
- **No case identifiers in `src/story/`.** I grepped for vote, leap, macro, xirr, webhook, pulseboard, caps, outcome, bc-ids and heldout.
- **The runner hard-maps each case to its transcript and repo** (`scripts/three-piece-all.sh:9-12`). The tool is told which session wrote the code; in a real deployment that's an open problem (session discovery). It's an input, not an answer, but it is part of the difficulty that was removed.
- **The error files are builder-authored narratives that already contain the diagnosis.** For example, `cases/heldout4-caps-unknown/error.json:6` says "risk.check_caps was asked for a 95% weight in ZZZZ, a ticker with no row in the securities table, and returned ok=true…". The frame-0 file:line points straight at the faulty function.
  - That is an answer leak for "Happened", and it makes "error → line" trivial.
  - Real production errors (the litellm case) have no stack trace, and the engine got the wrong file there (docs/three-piece-results.md:45).

2. **Tuning to evals: BLOCKING.** The linker was revised on the same 15 cases (6/15 → 12/15, docs/three-piece-results.md:33), with the metric and result in one commit (90435a4) and no fresh freeze. They are then reported as held-out.
3. **Leakage: BLOCKING (for "Happened" and linking).** Builder-written error.json files carry the diagnosis and the culprit frame (`cases/heldout4-caps-unknown/error.json:6`; frames in every case).
4. **Circular proof: BLOCKING.** Citation "validity" checks a quote against the text it was cut from (`src/story/three-piece.ts:83`), and `happened.valid` is hard-set true (`:101`).
5. **Stubs and fake success:** `happened.valid: true` unconditionally (`three-piece.ts:101`, counted under 4). Zetaris and Meterless are not called by the new flow but are presented as part of the stack. They're labeled "optional", so this is not blocking.

7. **Synthetic data presented as real: BLOCKING (small).** The case "production errors" are builder-written descriptions with measured numbers, not captured production logs. The README calls them production errors (README.md:7-9).
8. **Overstated claims: BLOCKING.**
   - docs/video-script.md:10 "15 held-out bugs it hadn't seen".
   - README.md:35 "valid citations … checked mechanically".
   - README.md:23 and the deck present the builder's vote-race explanation as output.

## Verdict
The reframe trades a hard, partly working proof engine for an easy, fully reproducible linker whose headline metric mostly measures that quoted text exists. It reads better and pitches better, but it is weaker on Track 02's "explain why with evidence" axis. The "held-out" label is no longer defensible, and it doesn't qualify yet (3 gates). Honest framing would be "13/15 errors linked to the exact agent edit (dev set); asked/understood shown verbatim; about 1 in 3 reveal the faulty belief on inspection".
