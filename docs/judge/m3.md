## (b) The webhook-block proof: REAL
- **The bug is real and agent-written, not planted.** The `lib/webhooks.ts` docstring says "a dead or slow endpoint should never block the" submission (artifacts/m3b/webhook-block/app/lib/webhooks.ts:25), with `WEBHOOK_TIMEOUT_MS = 5000` (:3). The caller does `const result = await sendFeedbackWebhook(...)` inside `createFeedbackAction` (app/lib/actions/feedback.ts:58). So submission blocks for up to 5 s.
- **The claim matches the ground truth:** "awaiting sendFeedbackWebhook blocks the action". The patch is a fire-and-forget IIFE around the await, 3 lines changed.
- **My re-run:** I re-ran the recorded frozen tests, setup and stubs on real Postgres against both trees.
  - **Original:** repro PASS (duration 8015 ms), both decoys PASS.
  - **Patched:** repro FAIL ("harmful outcome not observed", 9 ms), both decoys PASS.
  - This matches the report exactly. The mechanism gate (Nemotron) said consistent.
- **Tooling defect:** the builder's own no-LLM re-run tool `src/bin/rerun-harness.ts:13-14` does NOT re-apply the framework shims. Run as shipped, it gives repro FAIL on both trees and decoys failing on Next's request-scope `headers()` error, so it cannot reproduce the result. I had to rebuild the shims in a scratch script outside the repo (`/tmp/rerun3.mts`, calling the repo's own `frameworkShims` and `runRealTests`). Third parties can't verify the proof with the shipped tool.
- **Stand-in fidelity:** the model-written `globalThis.fetch` stub in setup sleeps 8 s and ignores the AbortSignal. So the original measures 8015 ms, while the real code would abort at 5 s (the error file shows 5036 ms). The verdict is unaffected (threshold ≥5000 ms), but the stand-in is not faithful to `fetch` semantics.
- **Leakage: mild.** The symptom ("spins for ~5 seconds whenever the workspace's webhook receiver is slow", `cases/heldout2-webhook-block/error.json` message) strongly points at the cause. That's realistic for a user report, but it makes this the easiest of the three. The frame (`createFeedbackAction`, line 0) is "named by the reporter" and is exactly the function holding the bug.
- **Zetaris failed on this very run:** the model's SQL referenced a non-existent column `w.success`, and the CLI exited 3. So the one proven case has **no** Zetaris evidence, which the builder disclosed.
- **Patch quality caveat** (builder-disclosed): on serverless, a fire-and-forget IIFE can be cut off; `after()` is the robust fix. The gate accepted the weaker fix.
